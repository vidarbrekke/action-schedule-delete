- The fewer lines of code, the better
- Proceed like a Senior Developer // 10x engineer
- Do not stop until ....

If there is a difficult error:
Fix the error, but start by writing 4 reasoning paragraphs analyzing what the error might be. DO NOT JUMP TO CONCLUSIONS. Quiet your ego, constantly question your assumptions. Come up with 4 plausible fixes and evaluate each fix, given what has already been attempted. Then decide on the best option and justify it. Once you have implemented a solution, review the code for potential bugs or optimizations before you finalize the task.

# when starting a new chat (when the previous chat becomes overloaded by previous context)

We will hand this project over to a new developer to continue  where you left off. Please summarize the current state of the project. format this as 5 paragraphs, where you describe what we just did, what didn't work, which files have been updated/created, what mistakes to avoid, any key lessons/insights we have learned, what problems/errors we are facing, and anything else a programmer needs to work productively on this project.

Write in a conversational yet technical and informational tone, something like a README file on github that is very dense and without any fluff. Do NOT include any assumptions or theories, just the facts.

I expect to see 5 concise paragraphs, written as if you were giving instructions to another programmer, and this was ALL you could tell them.


# when offered an idea for a solution

**Your Task regarding your proposed changes**  

1. **Evaluate** four distinct refactoring or implementation strategies that:  
   - Minimize cognitive and runtime complexity  
   - Enforce **DRY** (eliminate duplication)  
   - Apply **YAGNI** (remove unneeded features)  
   - Scale gracefully as requirements grow  

2. **For each strategy** (one paragraph each):  
   - Describe the approach  
   - Explain how it meets the four criteria above  

3. **Compare** all four:  
   - Summarize their trade-offs side-by-side  
   - Pick the single best approach  

4. **Implement** your chosen solution:  
   - Provide runnable, concise code  
   - Avoid spaghetti or technical-debt patterns  

**Guidelines**  
- Don’t rush—seriously weigh all four.  
- Keep prose tight and grounded in best practices.  
- Deliver a purposeful, debt-free update ready to drop in.

# when there is a bug fix that doesn't work
**Your Debug Task**  
1. **Review:** Examine the “Previous Attempts” and **do not** repeat any of those fixes.  
2. **Diagnose:** List four new, plausible root causes—each tied to a symptom or line of code.  
3. **Propose:** For each cause, suggest a concise fix that:  
   - Resolves the issue  
   - Enforces **DRY** (no repetition)  
   - Honors **YAGNI** (no unneeded complexity)  
4. **Select:** Pick the most likely cause based on simplicity and impact.  
5. **Implement:** Show the updated code snippet with that fix—lean, maintainable, and free of technical debt.  
6. **Verify:** Explain how to test it to confirm the bug is gone without regressions.

**Guidelines**  
- Keep each diagnosis/proposal to one short paragraph.  
- Ground every suggestion in the code or error output.  
- Deliver only runnable, minimal changes.  
- Emphasize simplicity, scalability, and maintainability.
